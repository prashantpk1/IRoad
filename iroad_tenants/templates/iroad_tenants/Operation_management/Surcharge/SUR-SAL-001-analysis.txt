1. OVERVIEW & STRATEGY — 78/100
================================================================================

What the spec says:
  - Use transactional surcharge records (not a simple extra-charges table).
  - Split Sales (revenue) and Purchase (cost).
  - Shipment is the ONLY reference; client/currency come from shipment.
  - One service per transaction (no sub-lines).

What we have:
  [OK]  Sales transactions stored as TenantShipmentSurcharge (one service row).
  [OK]  Create/edit/list UI for Surcharge Sales Transaction exists.
  [OK]  Shipment dropdown is source of truth; booking/client/currency derived.
  [OK]  No line subform — single header transaction per save.
  [GAP] Purchase module (SUR-PUR-001) not built — no purchase form, no vendor flow.
  [GAP] Entity name in code is TenantShipmentSurcharge, not SurchargeSalesTransaction
        (same role, different name).

Simple verdict:
  Sales side matches the strategy well. Full addendum is incomplete because
  Purchase (cost) side is missing.

4.1 Shipment Financials (spec)
--------------------------------
  Spec wants ON Shipment:
    surcharges_revenue = Sum(confirmed SALES total_amount)
    surcharges_cost    = Sum(confirmed PURCHASE total_amount)
    gross_profit       = (Freight Revenue + Surcharges Revenue)
                         - (Freight Cost + Surcharges Cost)

  Code today:
    [PARTIAL] TenantShipment.total_additional_charges property sums ALL
              surcharge subtotals (any status), not only Confirmed sales.
    [MISSING] No surcharges_revenue field on shipment.
    [MISSING] No surcharges_cost field on shipment.
    [MISSING] No gross_profit field on shipment.
    [MISSING] No auto-update when surcharge status changes to Confirmed.

              Draft and other statuses too.
    [GAP]     Pull is by booking/date range, not strictly "per shipment invoice".
    [OK]      Confirmed surcharge subtotal used as amount in report rows.
