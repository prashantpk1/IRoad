Reading Guide

Three things to know before reading any chapter. They explain what is in the document, what is deliberately excluded, and how to navigate cross-references.

i.1What is in scope

Twelve modules, all built and visible in the current product. Booking through Sales Invoice Reports for the Credit path; Booking through Driver Treasury Transaction for the COD path. The Driver Mobile App is documented for the screens that fire operational actions (job listing, job detail, POD upload, payment collection, wallet view).

i.2What is deliberately excluded

  • Vendor / Purchase flows — Purchase Invoice, Surcharge Purchase Transaction, Vendor Pay treasury classification. Removed from the Phase 1 product scope.
  • Treasury Master — a registry of bank accounts and cash boxes. It carries no operational logic; Driver Treasury wallets are noted once inside Chapter 13 as rows in this registry.
  • Reports and read-only views — screens that only render saved fields without any operational logic of their own (Rule R-13 of the Editorial Charter).
  • Future enhancements — the seven proposed engine enhancements (E1–E7) from earlier drafts. Pending business approval; mentioned only where directly relevant.

i.3How each chapter is structured

Every module chapter (Ch. 3 onwards) follows the same six-section skeleton:

  1. Identity Card — what the module is, why it exists, where it sits in the layered model.
  2. Screen anatomies — Summary screen (KPIs, filters, per-row actions); Form screen (where data enters); Detail screen (only when it carries logic the Form does not).
  3. State Model — values, transitions, derivation rules. State values come from the Phase 0 State Registry.
  4. Workflow & Effects — the operational flow, including auto-creates and downstream impacts on other modules.
  5. Cancellation · Updates · Intervention — what can be changed, when, by whom; cancellation conditions; admin intervention paths.
  6. Cross-references — closing pointer to other modules, drawn strictly from the Phase 0 Entity Relationship snapshot.

i.4Conventions used throughout

Module names

Always the canonical name from the live screen H1: Booking, Shipment, Shipment POD (not "POD Analysis"), Driver Treasury Transaction, etc. PNG filenames and PCS labels are never followed.

Status badges

Colour-coded throughout: ops for normal forward states, amber for proof or pending states, green for terminal success, crimson for cancellation or rejection, slate for neutral starts, admin for admin-only paths.

Diagram captions

Mermaid diagrams carry captions like D1.2 (chapter 1, second diagram) or D11.1. Captions appear in monospace below the figure.

Cross-references

Pointers like "see § 3.5" or "see Ch. 7" mean a specific section or chapter in this document. Mentions of "P1A" or "P3B" are historical references to the four prior drafts; they exist only in this front matter.

1.1.1Two closure paths

PathTriggerSequence
Credit Order Type = Credit Booking → Shipment → POD compliant → Sales Invoice Report (collection is downstream, handled by external accounting and out of Phase 1 scope)

1.1.2What the lifecycle guarantees

  • Single origin. Operational records cannot be born from anywhere except a Booking. There is no "create Shipment directly" path on any screen.
  • Single terminus. Every billable event flows into one report type. This is what makes the financial reporting layer tractable.
  • One branch, no further forks. The COD vs Credit decision happens once, at the Booking level (via Order Type), and is inherited by the Shipment. Past that point, the lifecycle does not branch again.
Why a single terminus matters
Treating SIR as the only terminus simplifies the financial reporting boundary: anything billable in IRoute ends up in an SIR. The COD path adds a settlement step (cash moves before invoicing) but does not invent a parallel report type. 01 · Architecture

Five Engine Principles

These five principles govern every decision in the Action Engine. Together they explain why drivers cannot undo, why admins cannot edit history, why a partially-executed Round Trip is still considered Executed, and why state fields are projections rather than stored values. All five are binding — violating any one breaks the model.

01
Append-Only Log action_log
Action Log entries are never edited and never deleted. Every correction is a new entry written on top of history. The original record stays intact for audit, even when its effect is later overridden.
Concrete example
Driver presses "Confirm Loaded" by mistake. Admin appends a corrective entry. Both records remain in the log; the new one wins for state derivation.
Common misconception
"Admin can delete the wrong entry." No — Admin can only append.
02
Latest-Action-Wins derive_from(log)
Entity state is not stored as a fixed value; it is derived from the most recent valid Action Log entry. Appending a new entry recomputes the state without touching prior entries.
Concrete example
Shipment shows In Transit because that was the last accepted action. Admin appends a corrective "At Delivery" entry → state recomputes to At Delivery.
Common misconception
"Status is a stored field that Admin overrides directly." No — status is always computed from the log.
03
Atomic Posting all-or-nothing
An action is committed only if all required evidence is captured: GPS, photos, video, notes — whatever the Action Master demands. If any required evidence is missing (e.g., the driver closes the app mid-action), nothing happens. The driver returns to the screen of the last valid action.
Concrete example
Driver taps "Confirm Loaded", the app requires 3 photos. Driver uploads 2 then closes the app. Result: action never recorded, Shipment never created, Truck Movement never created.
Common misconception
"A failed action leaves a partial record." No — the system treats it as if the action never happened.
Driver app has no Undo
There is no "back" or "revert" button on the driver's mobile app. If a driver presses the wrong action and it commits (evidence was complete), the driver calls Admin via the On Call feature. Admin appends a corrective entry to the Action Log. The original entry remains in the log permanently.

1.3Five Engine Principles — continued

04
Single-Step Cancel no gradual revert
Cancellation is one administrative decision taken when all prerequisites are clear. There is no "revert to previous stage → previous stage → cancel" sequence. Either conditions allow cancellation in one move, or cancellation is forbidden entirely.
Concrete example
Shipment is In Transit and Admin wants to cancel. The path is NOT: revert to At Delivery → revert to Loaded → cancel. Once past Loaded, cancel is forbidden; errors are corrected by compensating entries (Sales Adjustment, etc.), not by cancellation.
Common misconception
"Admin walks back the workflow step by step." Rejected as unrealistic — too brittle, no operational value.
05
Cancelled = Excluded archive, not erase
A cancelled record is archived but excluded from all calculations, KPIs, and derived states. It remains visible for audit. It does not count as a partial execution, a failure, or a degradation of performance metrics.
Concrete example
Round Trip with Item 1 Executed and Item 2 Cancelled. Booking status = Executed, not "Partial". The cancelled Item is excluded from the computation entirely.
Common misconception
"A Round Trip with one cancelled Item is partially complete." No — the cancelled Item is treated as if it never existed for the calculation.

1.3.1How the principles compose

The principles reinforce each other. Append-Only + Latest-Action-Wins together mean state is always reproducible from history. Atomic Posting prevents partial corruption. Single-Step Cancel prevents long, fragile undo chains. Cancelled = Excluded keeps reporting clean despite cancellations being recorded.

Engineering implication
State fields (booking_status, shipment_status, etc.) are projections, not sources of truth. Any rebuild of state from the Action Log must produce the same answer the live UI shows. This is verifiable and testable; it is the architectural backbone of every chapter that follows.
Admin's only tool
Given the five principles, Admin's only intervention mechanism is appending corrective entries to the Action Log. Combined with compensating financial entries (Sales Adjustments, Driver Treasury counter-entries), this covers every operational error documented in the seven scenarios in Chapter 15.

Credit vs COD · the only branch

The Order Type is set on the Booking at creation and inherited by the Shipment. It is the single branching decision in the entire system. Most modules behave identically for both paths; the differences are tightly localised to Shipment closure rules, Driver Treasury Transaction (COD only), and a small handful of validations.

1.5.1Where the two paths diverge

Module / ConcernCredit pathCOD path
Booking Order Type = Credit. COD Amount field hidden / not required. Order Type = COD. COD Amount required at Booking level.
Shipment Inherits Order Type = Credit. COD Amount and COD Payment Status fields not in play. Inherits Order Type = COD. COD Amount and COD Payment Status (Pending · Collected) are tracked.
Shipment closure gate Closure (Action 10) requires only that POD is compliant. Closure requires POD compliant and COD Payment Status = Collected. The system blocks the transition otherwise.
Driver Mobile App After Upload POD (Action 7), the next screen is the closure flow. After Upload POD, a Collect Payment screen surfaces. Driver collects cash; Action 9 fires.
Driver Treasury Transaction Not involved. Action 9 auto-creates a Driver Treasury Transaction (Debit · Client Pay) on the driver's wallet. Internal Transfer pair moves cash to a collection wallet at handover.
Sales Invoice Reports Aggregates the closed Shipment normally. Aggregates the closed Shipment normally. The fact that cash was collected upstream does not change SIR mechanics.

1.5.2Where the two paths are identical

Every other module behaves the same regardless of Order Type:

  • Surcharge Sales Transaction — extras are recorded against the Shipment without reference to Credit / COD.
  • Shipment Documents · Shipment POD · Document Handover — the three-step proof pipeline is identical.
  • Truck Movement Log — the asset ledger is identical.
  • Action Master · Action Log — the action set is the same. Action 9 (Collect Payment) is configured with a conditional prerequisite of Order Type = COD on the Action Master row.
Why this matters for the rest of the document
Because the branch is so tightly localised, most chapters do not have to discuss Credit vs COD at all. The chapters that do (Booking, Shipment, Driver Treasury Transaction, Driver Mobile App) say so explicitly. Outside those, the absence of mention is intentional — not an omission.

02 · The Action Engine

Reversal Actions · the admin paths

Four Admin-only actions handle the exceptional paths the ten Forward Actions cannot. They do not exist on the driver's app. They cancel records, reject evidence, or otherwise mark the system's view of an event as superseded — while still leaving every original record visible (Principle 1).

ID Action Visibility Effect & constraints
R1 Cancel Shipment Admin only Shipment = Cancelled. Theoretically only before Loaded, but since the Shipment is born at Loaded, R1 is effectively unreachable in normal operation. Reserved for documented exceptional cases. Once a Shipment is past Loaded, cancellation is replaced by compensating entries (Principle 4 · Single-Step Cancel).
R2 Cancel Booking Item Admin only Booking Item = Cancelled. Allowed when no Shipment exists for this Item. The Booking's derived status recomputes; a Round-Trip Booking with one Item cancelled is still Executed (Principle 5 · Cancelled = Excluded).
R3 Cancel Booking (whole) Admin only Booking = Cancelled. Allowed only when no Shipment exists on any Item. Once any Item is past Loaded, R3 is blocked — the Item must be handled individually.
R4 Reject POD Admin only POD Record = Rejected. Driver app reopens Action 7 (Upload POD). The rejected POD Record stays in the audit trail; a new POD Record is created when the driver re-uploads. The Shipment's POD Compliance flag recomputes accordingly.

2.2.1What reversal actions cannot do

  • Cannot delete any record. R1 / R2 / R3 archive with status Cancelled; R4 archives the rejected POD Record. Nothing physically disappears.
  • Cannot edit history. The original Action Log entries that led to the cancelled state remain in the log. The reversal is itself a new log entry on top.
  • Cannot rewind state through prior stages. A Shipment that reached In Transit cannot be reversed to At Delivery and then to Loaded. If the state is wrong, an Admin appends a corrective Action Log entry; the state recomputes (Principle 2).
  • Cannot cancel financial closure records. A Sales Invoice Report that has been Issued has no documented reversal; an erroneously Issued SIR is a known open thread. Recovery, if needed, is through external accounting adjustments outside the Phase 1 product.

2.2.2The relationship between Forward and Reversal actions

The two sets are not symmetric. The ten Forward Actions advance the operation; the four Reversal Actions handle the cases where the operation should not have advanced. There is no Reversal for A4 (Confirm Loaded) because once the Shipment exists, the principle of correction-by-appending takes over from cancellation. There is no Reversal for A9 (Collect Payment) because a cash variance is corrected with a compensating Driver Treasury Transaction (Reversal classification on a new row), not by undoing the original transaction.

Admin's discipline

02 · The Action Engine

Append-Only Log · what it guarantees

Action Log is the system's truth ledger. Every Forward Action and every Reversal Action produces exactly one Action Log entry — never zero, never more. The table is append-only by construction: there is no Edit button on any entry, no Delete button on any entry, no "amend" path anywhere in the UI. The audit trail is therefore complete and tamper-evident.

2.5.1What the log guarantees

  • Every action is recorded. There is no "silent" state change. Even Admin reversals (R1–R4) and Admin corrections are log entries.
  • No entry is ever lost. A rejected POD's original log entry stays. A cancelled Shipment's birth entry stays. A driver's wrong-button press, once committed, stays.
  • No entry is ever altered. The fields captured at the moment of firing — action code, user, source, GPS, evidence references, references to Booking / Shipment / Truck / Driver — are immutable.
  • State is reproducible. Replaying the log from the beginning, applying Latest-Action-Wins (§ 2.6), reconstructs every entity's current state exactly.

2.5.2What the log forbids

OperationWhy forbidden
Edit a logged action's effectWould silently re-interpret history. Correction is by a new entry; old entries are not retroactively changed.
Delete an action entryWould destroy audit. The deletion would be invisible after the fact — a tamper-proofness failure.
Backdate a new entryTimestamps capture wall-clock at firing. An admin appending a correction at 14:30 cannot record it as having happened at 09:00. The narrative about when the underlying event physically happened is in the entry's notes.
Insert an entry between two existing entriesThe log is strictly chronological. New entries are always appended at the tail.
Re-fire a successful actionAn action's prerequisite is the absence of the same action having already succeeded for the same entity. A second "Confirm Loaded" on the same Shipment is rejected before any log entry is written.

2.5.3Why this matters operationally

The combination of these guarantees yields three operational properties that the rest of the document depends on. First, every dispute is traceable — "who closed this job at 23:47?" has a single, unambiguous answer. Second, compliance reporting is straightforward — auditors are given read access to a table and the model is self-explanatory. Third, system recovery is principled — when a bug or a data correction is needed, the model has only one shape of fix (append), so there is no temptation to invent a one-off cleanup path that would break the invariants elsewhere.

A note on storage
The append-only log is conceptually one table. Physically, evidence (photos, videos, GPS traces) is stored alongside or referenced from the log entry. The principle holds for the references as well: an evidence file referenced by a log entry is itself immutable — new evidence on a corrective entry is new file storage, not an overwrite. Chapter 11 documents the Action Log schema in detail.

Latest-Action-Wins · state derivation

If the log is the truth, how does the UI know what state to show for a Shipment? It computes the state from the log. Specifically: for each entity (Booking Item, Shipment, Truck Movement, POD Record), the system finds the most recent valid Action Log entry that affects it, and projects its state accordingly. State fields shown in the UI are projections of history, not independently stored values.

2.6.1The derivation rule, stated precisely

For any entity E with state field S:

  1. Find all Action Log entries that reference E, ordered by timestamp ascending.
  2. For each entry, apply the Status Impact rule defined on its Action Master row.
  3. The final value of S is the value set by the last entry whose impact applies to S.
  4. If an entry was logically superseded by a later corrective entry (e.g., a wrong A5 followed by an Admin corrective A6), the corrective entry's effect dominates. Both entries are visible in the log; only the latest contributes to the current state.

2.6.2The decisive example

A corrective sequence
Suppose the driver fires A5 (Depart In Transit) for Shipment SH-001 at 09:00. The log records the entry; the Shipment state derives to In Transit. At 10:30, the driver realises they had not actually departed — they were still on site. The driver calls Admin. Admin appends a corrective Action Log entry at 10:35 reflecting that A5 was fired in error and the state should return to Loaded. The Shipment state recomputes; the UI now shows Loaded. Both entries remain in the log permanently. The 09:00 entry is not deleted — the system simply derives current state from the most recent applicable entry.

2.6.3What state derivation enables

  • Time-travel views. "What was the Shipment's state at noon yesterday?" is answered by replaying the log up to that timestamp. The Action Log Details screen surfaces this view.
  • State-machine validation. Because state is derived, the system can validate that no action is fired out of order: A5 requires a Shipment to exist; A7 requires the Shipment to be at At Delivery; A9 requires Order Type = COD and POD Submitted. These are configuration on the Action Master row (prerequisites), not hardcoded in the backend.
  • Reporting consistency. KPI counts — e.g., "Shipments in Transit" — are queries against the projection of state from the log. The same query produces the same answer regardless of which user runs it.

2.6.4What is not derived from the log

Not every field is derived. Configuration data (Action Master rows, Treasury Master rows, Service Items, Cargo Master rows) is stored normally and edited normally. Reference data (Booking Item Cargo, Truck assignment) is stored on the Booking and Shipment records. The derivation rule applies specifically to state fields — booking_item_status, shipment_status, movement_status, pod_status, cod_payment_status. The Phase 0 State Registry lists them; § 1.3 explains why they are projections rather than stored sources of truth.

A practical implication for chapter readers
Throughout this document, when a chapter says "Shipment status moves from A to B", what is happening physically is: an Action Log entry has been written, and the projection of state from the log now reads B instead of A. The phrasing is shortened for readability, but the mechanism is always derivation. If a chapter ever needs the longer phrasing, it says so explicitly.

The Round Trip Rule

A Round-trip Booking has two Items: Outbound and Inbound. Each Item executes independently — its own Shipment, its own POD, its own state. The decisive rule is what happens when one Item completes and the other is cancelled: the Booking is Executed, not "Partial". This is Engine Principle 5 (Cancelled = Excluded) applied to a multi-Item Booking.

3.6.1The decisive scenario

Round Booking with one cancelled Item

A Round Booking has 2 Items: Outbound (Riyadh → Jeddah) and Inbound (Jeddah → Riyadh). The Outbound Shipment closes cleanly — Item 1 reaches Executed. Before the return trip, the customer cancels the inbound leg; no Shipment was ever created for Item 2. Admin applies R2 to Item 2 — Item 2 reaches Cancelled. The Booking's derived status recomputes. With Cancelled excluded, the remaining set is {Item 1: Executed}. Booking status = Executed. Not "Partial". Not "Partially Executed". The cancelled Item is treated as if it never existed for the derivation.

3.6.2Why "Partial" is rejected

Earlier drafts of the model considered an intermediate Booking state called Partial. The team rejected it for two reasons. First, it complicates the projection — a query for "Bookings still requiring follow-up" has to enumerate two states (Active + Partial) instead of one. Second, it muddles reporting — revenue and KPIs need a clean "done" vs "in progress" cut. The chosen model treats cancellation as a clean exclusion, not a degradation.

3.6.3The general rule, stated precisely

For any Booking with Items I = {I1, I2, ...}:

  1. Compute I' = {i ∈ I : i.status ≠ Cancelled} — the non-cancelled subset.
  2. If I' = ∅ (every Item is cancelled), the Booking is Cancelled.
  3. If every i ∈ I' has status = Executed, the Booking is Executed.
  4. Otherwise (at least one i ∈ I' is Planned or In Execution), the Booking is Active.

3.6.4What this means for KPI queries

Active Bookings in the KPI strip use the pattern status NOT IN (Closed, Cancelled) consistently. Executed Bookings use status = Executed. The Round-Trip rule means a Booking with a cancelled return appears in the Executed KPI, not the Active KPI, and not a hypothetical Partial KPI. The list and the dashboard agree because both use the same projection.

4.8.2If something genuinely goes wrong after Loaded

The corrective playbook does not involve cancelling the Shipment. Instead, the system uses one of four paths depending on the nature of the problem:

  • Operational mistake (wrong action pressed, wrong address, wrong cargo): Admin appends corrective entries to the Action Log — Scenarios S1 and S3.
  • Bad POD (illegible, forged, incomplete): R4 (Reject POD) flips the POD Record to Rejected; the driver app reopens A7 for a fresh upload. Scenario S5.
  • Cash variance (driver delivered less or more than the COD Amount): a compensating Driver Treasury Transaction with classification Reversal plus a Sales Adjustment outside the operational flow. Scenario S6, developed in Ch. 13.
  • Asset failure mid-route (truck breakdown after Loaded): truck swap is documented via Update Truck (Admin override with reason); the Shipment continues under the new truck.

4.8.3What is never allowed

Three operations are structurally forbidden and not surfaced on any screen:

  • Deleting a Shipment record — blocked by the Anti-Delete rule.
  • Editing a past Action Log entry — the log is append-only (Engine Principle 1).
  • Rolling Shipment state backward (e.g., from In Transit back to Loaded) — Latest-Action-Wins means the only way to "undo" is to append a new action whose state impact resets the projection.

Workflow & Effects

The end-to-end Surcharge workflow runs from creation to either invoicing or cancellation. Most Surcharges are created reactively — Ops sees something happened in the field and records the charge. The Confirmed → Invoiced step is automatic; users rarely interact with it.

5.5.1Creation workflow

  1. Trigger — Ops user receives information about an extra cost (driver report, toll receipt, client request). User opens the Surcharge list and clicks "Create Surcharge Transaction."
  2. Anchor the record — select the Shipment Ref from the dropdown. Booking Ref and Client auto-populate.
  3. Capture the charge — choose Service from the filtered dropdown (service-type items only). Enter Quantity and Unit Price; Total Amount auto-calculates.
  4. Document the justification — write the Reason (free text) and upload the Attachment (file). Both required to advance past Draft.
  5. Save — Status = Draft. Record is editable.
  6. Confirm — when the data is correct and complete, user clicks Confirm. Status = Confirmed. Record is now locked, eligible for invoicing.
  7. Invoicing — at the next SIR aggregation run, this Surcharge is included. When SIR is issued, status flips to Invoiced automatically.

5.5.2What Surcharge is NOT

  • Not an edit of the Booking. The Booking's commercial scope is frozen at confirmation. Surcharges are additive, separate records.
  • Not a discount mechanism. Surcharge represents added cost only. Discounts and sales adjustments are a different module (Sales Adjustment / Credit Note — outside Phase 1 scope).
  • Not for product sales. Service filter blocks product-type items.
  • Not retroactive history rewriting. A Surcharge is dated when discovered, not back-dated to the original Booking date. Each Surcharge has its own Date field.

5.5.3Practical pattern · detention charge

A worked example
Driver waits 2 hours at pickup beyond the agreed window. Driver reports via On Call. Ops opens Surcharge → anchors to that Shipment → Service = "Detention Charge", Quantity = 2, Unit Price = 75 SAR → Total auto-calculates to 150 SAR. Reason: "Warehouse delayed loading by 2 hours." Attachment: waiting-receipt photo. Save → Confirm. At next SIR run, the 150 SAR is added to the customer's invoice for that Shipment.

5.5.4Scenarios that touch Surcharge

Per the Phase 0 Scenario Coverage Matrix, only one of the seven scenarios reaches Surcharge directly:

  • S6 · COD Collection Variance — when the driver collected the wrong amount of cash, the operational response involves a compensating Driver Treasury Transaction (Ch. 13) and, where the variance reflects a chargeable extra (e.g., service rendered but not in the original Booking), a new Surcharge. The Surcharge here is a normal new record — not a reversal of an earlier one.

The Pivotal Flag · Is Delivery Note?

One toggle on the Shipment Documents header decides whether that document gates POD compliance for the parent Shipment. Setting it to Yes makes the document a required leg of proof; setting it to No keeps the document on file but excludes it from the compliance computation. This single flag is what allows the same Document Type table to serve both the proof workflow and the regulatory / archival workflows without conflict.

6.4.1What the flag does, precisely

Flag valueEffect on POD complianceEffect on Document Handover
Yes — Is Delivery NoteThis document must reach header_status = Verified for the Shipment's pod_status to become Compliant. If multiple documents are marked Yes, all must be Verified.Each page declared in the subform must be matched by a row in Document Handover with Page Status = Received OK (Ch. 8).

6.4.2Why a flag, not a hardcoded type

A naive design would say "Delivery Note is always the proof; all other types are storage." Reality is messier: some clients accept the signed Commercial Invoice as proof; some operations use a custom "Receipt of Goods" certificate; some clients require multiple proofs (signed Delivery Note and stamped Bill of Lading). Hardcoding the type would force the operations team to either rename their actual documents or stretch the meaning of "Delivery Note" beyond what their clients understand. The flag-based approach lets each Shipment declare its own proof contract.

6.4.3Cascading consequences when the flag is Yes

  1. The Shipment's pod_doc_count increments by 1 (visible in the Shipment Form Section 2 from Ch. 4 § 4.3).
  2. The POD Compliance computation (Ch. 7 § 7.6) now treats this document as a required leg.
  3. Each page row in the subform becomes a tracked unit for the Document Handover process (Ch. 8).
  4. The Soft Copy field becomes operationally required — without an uploaded soft copy, the POD Record's Soft Copy Status cannot reach Collected.

6.4.4What the flag does not do

  • Does not change the Document Type. A Commercial Invoice marked Is Delivery Note = Yes is still a Commercial Invoice for type-classification purposes.
  • Does not lock the flag at Verified. If a Verified Document is later discovered to have been mistakenly marked Yes, the flag can be edited (with audit trail). This is operationally rare but the system allows it.
  • Does not propagate to other Shipments. The same Document Type can be Yes on one Shipment and No on another, even for the same client. Each Shipment is independent.
The flag is the only thing that matters for compliance
Throughout Ch. 7 (Shipment POD), when the chapter says "required documents", it means precisely the set {document : document.shipment = this AND document.is_delivery_note = Yes}. No other field, no other type-based heuristic. The reading is uniform.

POD Status · Auto-Derivation

The overall POD Status field on the POD Record is auto-derived from the three sub-statuses (Hard / Soft / Digital) plus the rejection flag. It is never typed by a user. This section states the derivation rule precisely so that a reader can predict the POD Status from the sub-statuses alone.

7.5.1The derivation rule

Derivation formula

Let H = POD Hard Copy Status, S = POD Soft Copy Status, D = POD Digital Evidence Status. Let R be true if any R4 (Reject POD) has been applied since the most recent upload.

  1. If R is true → POD Status = Rejected.
  2. Else if all of H, S, D reach their terminal verified value (H=Submitted, S=Verified, D=Verified) → POD Status = Finalized.
  3. Else if at least one of S, D reaches Verified (and no rejection) → POD Status = Verified.
  4. Else if any of S, D is at Collected (or higher) → POD Status = Collected.
  5. Else → POD Status = Pending (the default state at record birth).

7.5.3Why derive, not store

The POD Status is a function of the three sub-statuses. If it were stored independently, it could drift — a rejection on Soft Copy could be applied without the overall status updating, leaving the record in an inconsistent state. By deriving on read, the system guarantees the overall status always reflects current reality. This is the Latest-Action-Wins principle (Ch. 2 § 2.6) applied to a per-record derivation rather than to the global state projection.

A rejection persists in audit but not in the derivation

When the driver re-uploads, a new POD Record is created (§ 7.7) — the original rejected record stays in storage with its sub-status frozen at Rejected. The new record begins at Pending with all sub-statuses fresh. The Activity Log on the Shipment surfaces both records; the compliance derivation considers only the latest live POD Record per Shipment Documents row.

Compliance · Derivation Logic

The Shipment carries a derived field pod_status with two possible values: Compliant or Not Compliant. This field is never stored manually — it is recomputed every time any of the four layers changes. The rule is straightforward: a shipment is Compliant if and only if every required layer is satisfied.

7.6.1The compliance rule

Compliance formula

shipment.pod_status = Compliant if and only if all four conditions hold:

  1. All Shipment Documents on this Shipment flagged is_delivery_note = Yes have Header Status = Verified.
  2. The latest active POD Record has Digital Evidence Status = Verified.
  3. The latest active POD Record has Soft Copy Status = Collected or higher (Verified is acceptable; Rejected and Pending are not).
  4. For every page of every Delivery-Note document, the Document Handover sub-row marks the page as Received OK.

If any one condition fails, pod_status = Not Compliant.

7.6.2What "required" means in practice

Not all Shipment Documents are required for compliance. The Is Delivery Note? toggle (set on each document at Layer 0, Ch. 6 § 6.4) decides:

  • Is Delivery Note = Yes — the document is part of the compliance check. Its status and its handover entries gate Compliant.
  • Is Delivery Note = No — the document is stored for record-keeping but does not block compliance. Examples: Commercial Invoice, Packing List, Customs Declaration when not used as proof.

Rejection Path · R4 + Re-Upload

When Ops finds the uploaded POD unacceptable, they fire R4 · Reject POD with a documented reason. The rejected POD Record stays in the system permanently (Append-Only Log). The driver app reopens Action 7 (Upload POD), and the next successful upload creates a new POD Record. The Shipment then has two POD Records linked to it — one Rejected, one active. This is Scenario S5 in the Phase 0 Scenario Coverage Matrix.

7.7.1Why reject — common reasons

  • Soft Copy illegible — photo too blurry, partial scan, missing signature area.
  • Wrong document — driver uploaded an invoice instead of the signed Delivery Note.
  • GPS mismatch — captured location is far from the expected delivery point and no explanation exists.
  • Incomplete page set — only some pages of a multi-page document were captured.

7.7.2What R4 does, step by step

7.7.3What R4 does NOT do

  • Does not delete the original POD Record. It stays forever in the Anti-Delete Absolute class.
  • Does not edit the original. The status flips from Collected / Verified to Rejected, but every captured field (photos, GPS, Soft Copy attachment) is preserved unchanged.
  • Does not block compliance permanently. A clean re-upload restores the path to Finalized.
  • Does not move the Shipment backward. The Shipment's stored status does not revert. Only the derived pod_status recomputes.

7.7.4The audit story after rejection + re-upload

A Shipment that has been through R4 will show:

  • Two POD Records linked to it — POD-XXX (Rejected, with reason) + POD-YYY (Finalized).
  • Multiple Action Log entries — the original Upload POD, the R4 rejection action, the re-uploaded Action 7.
  • Activity Log on the latest POD Details view shows the clean path; the rejected record's Activity Log shows where things went wrong.
Why a new record, not an edit
Editing the original POD Record on re-upload would erase the rejection from the audit trail. Two records preserve the full story: someone took the time to reject the first attempt, someone (possibly the same driver) succeeded on the second. The customer, the insurer, and the regulator can all reconstruct exactly what happened.

8.5.2What happens when pages are Missing or Rejected

If the Header status is set to Missing or Rejected instead of Posted, the effect chain is different:

  • Missing. The verified-OK pages still update their Physical Location (they are in the company); the missing rows stay at their current location with a Note. 8.5.3What Posted cannot do

  • Cannot be reversed by editing. The Handover record is locked at Posted. Errors found after posting (e.g., a page was misfiled) are corrected by appending a new compensating Handover record — this is the Append-Only principle applied to Layer 3.
  • Cannot be deleted. Anti-Delete rule.
  • Cannot retroactively change a page's status. If a Posted Handover had a Received OK page that later turned out to be the wrong document, the correction is at the Doc Record / POD Record level (rejection of the document), not at the Handover level.

The recompute of pod_status on Handover post means that a Shipment which had been Compliant can become Not Compliant if a follow-up Handover discovers a missing page. This produces an operational alert — the Shipment appears in a "Closed but Not Compliant" report — which is the trigger for the candidate Scenario S8 follow-up workflow.

Two-Type Workflow

The two row types follow parallel but distinct workflows. Loaded movements are auto-cascaded by Action 4 firing on the driver app; Empty movements are explicitly initiated by the driver from the same app during On Call mode. Both paths originate at the driver — Admin never opens a TML row. This section walks through both end-to-end.

9.5.1Loaded movement workflow — driver-driven (auto-cascaded)

  1. Birth at A4 — driver fires Confirm Loaded on a Booking Item. The engine atomically creates: (a) a Shipment record, (b) a TML row in Scheduled state, (c) a Booking Item state advance to In Execution. All three or none (Engine Principle 3).
  2. A5 · Depart In Transit — driver fires departure. TML row's Status advances to In Progress, Start Time is stamped. Shipment status moves to In Transit in lockstep.
  3. A8 · Unloading Completed — driver fires after delivery completion. TML row's Status advances to Completed, End Time is stamped. This is the moment the asset-side leg closes.

The Shipment continues through its remaining states (POD Submitted, Delivered, Closed) but the TML row is now terminal. Asset-side closure happens before commercial-side closure, which is operationally correct — the truck has unloaded and is available for new work.

9.5.2Empty movement workflow — driver-initiated

The driver opens the Empty Move Workflow from the mobile app while in On Call mode (between assigned jobs). The workflow is a brief wizard that captures the leg's metadata before the truck moves.

  1. Open — driver taps Empty Move from the On Call screen. The app surfaces a three-step wizard (Ch. 14 § 14.7.4).
  2. Reason — driver picks one of three reasons: Return, Maintenance, or Repositioning.
  3. From and To — driver picks From Location and To Location.
  4. Submit — the app creates the TML row with Movement Source = Empty, Status = Scheduled, Truck and Driver inherited from the authenticated driver's profile.
  5. Start — when the truck departs, the driver taps Start on the same screen. Status advances to In Progress, Start Time is stamped. The row is now locked for editing.
  6. Complete — on arrival, the driver taps Complete. Status advances to Completed, End Time is stamped. The row is terminal.

Cancel (rare alternative): if the trip never happens (plan changed before departure), the driver can cancel while still in Scheduled — the row stays in storage with Status = Cancelled but is excluded from KPIs.

9.5.3The three Empty Move Reasons

ReasonOperational meaning
ReturnThe truck is returning to its base after completing a delivery. Typically the longest Empty leg per cycle — minimising it is a primary planning goal.
MaintenanceThe truck is moving for service, inspection, or repair. Distance is real; commercial value is zero. Tracked so that maintenance hours surface in utilisation reports.
RepositioningThe truck is moving between hubs to pre-position for an upcoming Booking. Often a sign of a fleet imbalance — high Repositioning counts suggest the dispatcher should reshape route assignments.
Loaded never cancels independently
The R1 (Cancel Shipment) action, which is the only path that would cancel a Loaded movement, is structurally unreachable in practice (Ch. 4 § 4.8). This means in normal operation, every Loaded TML row reaches Completed. Empty rows are the only ones that ever land in Cancelled.

10.1.1The heart of the system

The five engine principles in Ch. 1 § 1.3 are not enforced by code paths scattered through the application; they are enforced by Action Master rows. Append-Only Log is enforced by configuring every action to write to Action Log on fire. Latest-Action-Wins is enforced by the Status Impact columns. Master vs Log — the two halves of the engine
The engine is split into two modules. Action Master (this chapter) holds the rule. Action Log (Ch. 11) holds every time the rule fired. The Master is configuration; the Log is history. The Master is editable; the Log is append-only. The Master answers what would happen; the Log answers what did happen. Understanding the split is the prerequisite for both chapters.

The kebab menu carries View, Edit, Delete. Edit is always available to the Admin role. Editing an Action Master row updates the engine's rule going forward. Past Action Log entries retain their original effect — they were resolved against the row as it was at the moment of firing. Status derivation reads the current Action Master to interpret older log entries, however, so a change in Status Impact can retroactively change how derived states are computed. This is the only retroactive effect of editing a row; Admins are advised to keep the Notes field current to document such changes.

The Prerequisites field is a multi-select lookup into other Action Codes. Prerequisites encode the actual dependency graph; Sequence Number gives the default ordering. The two work together: Sequence Number for presentation, Prerequisites for enforcement.

Latest-Action-Wins

Engine Principle 2. The effective status of every entity in the system is derived from the most recent valid Action Log entry that targets that entity. The status is not stored as a fixed value; it is computed on read from the log. This section states the derivation rule precisely and walks through a worked example.

11.4.1The derivation rule, stated

Definition
For any entity (Booking, Booking Item, Shipment, Truck Movement, POD), its effective status equals the Status Impact declared by the Action Master row of the most recent Action Log entry that (a) references this entity, (b) has Source = Auto or Manual (i.e., is a valid entry), and (c) is not superseded by a later cancellation or reversal of itself.

11.4.3What "valid" excludes

Three conditions disqualify a log entry from contributing to derived state:

  • Source = neither Auto nor Manual. Entries from test runs or debugging tooling carry a different Source tag and are ignored by derivation. In production these do not exist.
  • The Action Master row referenced is Inactive at read time. If an Admin has retired an action since the log entry was written, derivation skips that entry. (This is a rare administrative move — usually deactivating an action is preceded by ensuring no live log entries reference it.)
  • A later reversal entry exists for this same firing. If a Reversal Action (R1, R2, R3, R4) has been logged that explicitly targets the same firing, the original is treated as superseded. The reversal entry itself becomes the latest.

11.4.4Time-travel queries

The same derivation logic, applied with a date-time cutoff, answers historical questions: "what was the Shipment's status at noon yesterday?". The query is: Pull all log entries for this Shipment with Log Date ≤ the cutoff, sort descending, take the top, look up its Status Impact. The answer is the historical status as of the cutoff. The Action Log Details view supports this directly — it surfaces the projection of state from the log at any chosen point in time.

Eligibility Gates

The Auto Post sweep is not unconditional. Four gates filter what flows into the report; rows that miss any gate stay invisible. The gates derive from POD compliance (Ch. 7), the Closed status trigger (Ch. 4), and the cross-cutting Cancelled-Excluded principle (Ch. 1 § 1.3).

12.4.1The four gates

GateRule
Gate 1 · Shipment ClosedA Shipment becomes Closed automatically when POD = Compliant AND, for COD orders, the Driver Treasury Transaction sequence has settled (Internal Transfer completed). Until Closed, the Shipment cannot be billed and is silently skipped by the sweep.
Gate 2 · POD CompliantCompliance requires the four conditions from Ch. 7 § 7.6: all Is-Delivery-Note documents Verified, Digital Evidence Verified, Soft Copy Collected (or higher), all Hard Copy pages Received OK via Document Handover. Anything less and the Shipment is not Closed, so Gate 1 fails. Gates are nested, not independent.

12.5.3The Issue transition · what happens atomically

The Issue button on a Draft fires the following atomic sequence (Engine Principle 3 · Atomic Posting):

  1. SIR's status → Issued; issue_date stamped.
  2. For every Surcharge in the report's Surcharges table: status → Invoiced; the Surcharge's Action Log gets an entry.
  3. For every Booking in the Bookings table: Sales Report field → this JOR's ID.
  4. For every Shipment in the Related Shipments table: Sales Report field → this JOR's ID.
  5. An Action Log entry is appended recording the Issue action with the admin user and timestamp.

All five writes succeed together or all roll back. Issuing a SIR that includes 10 Bookings and 3 Surcharges produces 14 backlinks plus 4 status changes plus 1 audit entry in a single transaction.

Deleting a Draft is safe; deleting an Issued report is impossible
Drafts have no downstream effects — no Surcharge has been flipped, no Booking has been backlinked. Deleting a Draft simply discards it. An Issued report, by contrast, has touched many other records; reversing it would require corrective entries throughout. The system blocks Delete on Issued reports entirely; the corrective path is a Credit Note (issued outside IRoute as part of the accounting workflow).

Classifications & the Internal Transfer Pair

Three production classifications carry the COD-collection narrative. Client Pay records the moment a driver receives cash from a customer. Transfer Out + Transfer In together coordinate the handover from the driver's wallet to a designated collection wallet. Reversal corrects errors. The Internal Transfer pair is the mechanism by which cash collected in the field moves between wallets within the system.

13.5.1The Internal Transfer — why two rows for one event

The handover of collected cash from one wallet to another is, accounting-wise, one event but two rows — because two wallets are touched. The source wallet (the driver returning cash) gets a Credit with Classification Transfer Out. The destination wallet (typically a designated collection wallet held by the admin or finance operator) gets a Debit with Classification Transfer In. Both rows share one Linked Source identifier — Transfer TRN-NNNN — so an auditor can recover the pair from either side of the ledger.

13.5.3The atomicity guarantee

An Internal Transfer commits both rows in a single database transaction (Engine Principle 3 · Atomic Posting). If the destination wallet write fails for any reason — permissions, deleted wallet, system error — the source wallet write rolls back too. There is no scenario where a Transfer Out exists without its matching Transfer In; both rows are created or neither row is created. The two are inseparable.

13.5.4The Reversal classification

A Reversal row is the corrective entry for a mistake. The pattern:

  1. Original erroneous row TT-000050 (e.g., a Client Pay Debit of 5,000 against the wrong driver wallet).
  2. Admin posts TT-000098 with Classification = Reversal, Type = opposite of original (Credit), Amount = same (5,000), Linked Source referencing TT-000050.
  3. The erroneous driver wallet's balance is restored to its pre-error value (net effect of TT-000050 + TT-000098 = zero).
  4. Admin then posts the correct row TT-000099 against the right driver wallet.

Three rows in storage; original error preserved; correction is auditable. The driver wallet balance arithmetic works out exactly.

The KPI counts events, not rows
The Internal Transfers KPI on the list page counts events (Transfer Out + Transfer In pair = 1 event). A value of 4 transfers means 8 underlying rows. The Total Trx KPI counts rows directly. The disparity is operationally meaningful — the finance team usually wants the event count for "how many handovers happened today?", not the row count.

A COD Shipment cannot reach Closed until two things are true simultaneously: POD is Compliant (the proof gate, Ch. 7) and the COD cash has been collected and settled (the cash gate, this chapter). A "COD Collected" status by itself only proves the driver took the cash. A "wallet net zero" proves the driver also handed the cash over to the company. Without the second condition, a driver could conceivably leave the system holding uncollected funds indefinitely. The Internal Transfer is what closes that loop. Offline Behaviour

Connectivity in the field is not guaranteed. The app's offline behaviour is deliberate: it degrades gracefully to read-only mode, surfaces clear indicators, and waits for reconnection rather than buffering writes that would later conflict. This is the structural reason the system never has a half-fired action — if the network is unavailable, the action does not fire at all.

14.6.2Why no write buffering

A naive design would queue Forward Actions while offline and replay them on reconnect. The system explicitly rejects this approach for three reasons:

  • Atomicity guarantee. An action's downstream effects (Shipment creation, TML creation, status push, treasury entry) require atomic database commits. The backend cannot atomically commit at the moment the driver tapped — it can only commit at the moment of reconnect. The temporal lie is too dangerous.
  • State staleness. By the time the device reconnects, the backend state may have changed (Admin cancelled the Booking via R3, for example). A replayed action against stale state could write conflicting effects.
  • Audit clarity. The Action Log entry's timestamp must reflect when the action committed, not when the driver tapped. Buffering would force a choice between two timestamps, neither of which tells the full story.

14.6.3The Home Page · Offline Screen

When the app detects no connectivity (failed heartbeat, failed API call, OS-reported network state), it switches to a visually distinct variant of the Home screen:

  • Banner: red strip at the top reading "No connection — reconnect to continue working" (or local-language equivalent).
  • Job card: shown read-only with last-known state. The next-action button is replaced by a greyed-out placeholder.
  • Empty-move quick entry: disabled.
  • History tab: accessible (cached); past job details are readable.
  • Profile tab: accessible; the driver can review their profile and change password (the change is queued until reconnect).

14.6.4Recovery on reconnect

When connectivity is restored:

  1. The app detects the network state change (OS callback or successful heartbeat retry).
  2. It removes the offline banner.
  3. It re-fetches the driver's current Job state from the backend — this is the canonical source of truth, overriding any cached state.
  4. If the driver had been mid-evidence-capture (photos taken offline), the capture state is preserved — the driver can complete the upload and submit.
  5. The next-action button re-enables based on the freshly fetched state.
Scenario S7 maps to this behaviour
Scenario S7 (Failed Action / App Closed) in the Phase 0 matrix is the operational case where the driver tapped an action, the app crashed or closed before the backend confirmed commit, and the action was never actually fired. The atomic-commit-only model means the driver simply re-fires on the next launch — the system state is exactly as it was before the tap. No partial state, no replay, no cleanup needed.

15.3.2The wallet-net-zero gate

For COD orders, the Shipment cannot reach Closed until two conditions hold simultaneously:

  • POD = Compliant (same gate as Credit, per Ch. 7 § 7.6).
  • Wallet net contribution = zero — the Client Pay debit on the driver wallet has been balanced by the Transfer Out credit, meaning the driver no longer holds company cash from this Shipment.

Both legs of the Internal Transfer must commit for the second condition to hold. A driver who has collected COD cash but has not yet completed the Internal Transfer leaves the Shipment stuck at Delivered — not Closed, not billable.

Seven Canonical Scenarios

The seven scenarios from the Phase 0 Coverage Matrix, each developed with the corrective steps the system follows. Each scenario references the chapter sections where its local impact is documented; this page provides the consolidated walkthrough.

15.4.1S1 · Field-Error Correction

Driver pressed wrong button or entered wrong value

Trigger. Driver fires A6 (Delivery Arrival) accidentally at a stop that was not the actual delivery point. The Shipment now reads At Delivery, but the truck is in fact still En Route. Correction. Admin appends a corrective action via the Action Log surface — firing A5 again with a Note explaining the override. Latest-Action-Wins (P2) makes A5 the current state declaration; the Shipment derives back to In Transit. The original A6 entry stays in the log forever as audit evidence of the error. Records. Both A6 and corrective-A5 are visible in the Activity Log; the timeline tells the full story. (Ch. 4 § 4.7, Ch. 11 § 11.5)

15.4.2S2 · Cancel Item in Round Trip

Round Booking with one Item completed and the other cancelled

Trigger. Round Booking with 2 Items: Outbound (Riyadh → Jeddah) and Inbound (Jeddah → Riyadh). Outbound Shipment closes cleanly; Item 1 reaches Executed. Customer cancels the return leg before any Shipment exists for Item 2. Correction. Admin applies R2 to Item 2 with a documented reason. The Item moves to Cancelled; the reserved Truck and Driver for that date are released. Booking derivation. The Booking's derived state recomputes. With Cancelled excluded (P5), the remaining set is {Item 1: Executed}. Booking status = Executed, not "Partial". The cancelled Item is treated as if it never existed for the derivation. (Ch. 3 § 3.6)

15.4.3S3 · Update Address Mid-Execution

Customer requests delivery to a different sister branch

Trigger. Shipment is In Transit. The customer calls Ops requesting delivery to a different branch — the original address is closed. Action. Admin fires Update Address (delivery side) from the Shipment list. The cutoff window (Ch. 4 § 4.7) allows changes to the Delivery Address until the Shipment reaches At Delivery; In Transit is still within the window. Effect. The Delivery Address Line is updated; an Action Log entry records the old value, new value, reason, and user. The driver's app shows the updated delivery point on the next refresh. (Ch. 4 § 4.7)

15.4.4S4 · Update Cargo Before Loaded

Driver counts actual cargo and finds it differs from planned

Trigger. Driver at loading site. Booking plans 20 tons; actual loaded is 22 tons. Action. Driver applies Update Cargo from the Job Detail · Loading screen before tapping Confirm Loaded (A4). The Cargo subform on the Shipment-to-be is updated; the change is allowed because the Shipment is not yet Loaded (cutoff window per Ch. 4 § 4.7). Effect. Cargo lines updated; Total Cargo Weight recomputed. When A4 fires moments later, the Shipment is born with the corrected cargo values. The Booking's original cargo line is preserved for audit reference. (Ch. 4 § 4.7)

15.4.5S5 · Reject POD and Re-upload

Ops finds uploaded POD illegible or incomplete

Trigger. Driver fires A7. POD Record created with Soft Copy attached. Ops opens the Detail view and finds the signature page is blurry beyond legibility. Action. Ops fires R4 (Reject POD) with a documented reason. Effect. Original POD Record's status flips to Rejected; the record stays in storage permanently. Driver app reopens A7 (Upload POD) as available. Driver retakes the photo and re-fires A7. A new POD Record is created (different ID); the original Rejected record remains intact. Shipment's pod_status stays Not Compliant until the new POD is verified. (Ch. 7 § 7.7)

15.4.6S6 · COD Collection Variance

Driver collected cash differing from the expected COD Amount

Trigger. Booking COD Amount = 1,500 SAR. Driver enters 1,400 on the Collect Payment screen with Note "Customer paid 1,400 only, claims discount agreement." Action. A9 fires with 1,400. TT row created (Client Pay Debit) with the actual amount. Shipment surfaces the variance in the Ops dashboard. Resolution paths. Either (a) Ops issues a Sales Adjustment outside IRoute reducing the SIR amount to 1,400 — the Shipment then closes against the corrected total; or (b) Ops escalates and the customer pays the 100 SAR difference, recorded as a second TT row (manual entry, Client Pay Debit). The driver wallet then settles via Internal Transfer of the full collected amount. (Ch. 13 § 13.7.2)

15.4.7S7 · Failed Action (App Closed Mid-Capture)

Driver app crashed or closed before backend confirmed commit

Trigger. Driver taps Confirm Loaded (A4). Evidence is being captured. Network drops or app crashes before the backend confirms commit. Effect. Atomic Posting (P3) means the action did not commit. No Action Log entry, no Shipment created, no TML row created. Booking Item stays Planned. Recovery. Driver reopens the app; lands on the Job Detail · Loading screen (the last valid state before A4 was attempted). The Confirm Loaded button surfaces again with the same evidence requirements. Driver re-fires A4. The system state is exactly as it was before the failed tap — no cleanup, no orphan records. (Ch. 4 § 4.4, Ch. 14 § 14.6.4)

Four engine principles bound the entire system. Each was introduced in Ch. 1 § 1.3 and referenced throughout subsequent chapters. 15.6.1P1 · Append-Only Log

The Action Log is structurally append-only at the database layer; the application surface does not expose Edit or Delete. Corrections happen by appending new entries that reference originals; Latest-Action-Wins (P2) then makes the correction authoritative.

15.6.2P2 · Latest-Action-Wins

Every entity's effective status is derived from the most recent valid Action Log entry that targets it. Status is never stored as a fixed value to be maintained; it is computed on read. This is what makes corrections cheap (append, do not edit) and what makes time-travel queries trivial (filter by date cutoff, sort, take top).

Cancellation is one decision, not a sequence. If the conditions to cancel are satisfied, the action commits in a single move; if not, the request is rejected outright with no gradual workaround.
